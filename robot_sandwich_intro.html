Communication Spine // Exercise 00

How to Teach
a Robot to Make
a Sandwich 

Before we write a single line of code, a question that turns out to be the whole job: how do you give an instruction that can't be misread?

press → or space to begin
The Setup // 01

Meet your robot.

It is fast, tireless, and follows orders perfectly. It has exactly one flaw: it does precisely what you say and nothing you merely meant.

No common sense. No benefit of the doubt. No "you know what I mean." It is the most literal thing you will ever work with.

// sound familiar? hold that thought.

The Mission // 02

Your order is simple.

YOU → ROBOT

"Make me a sandwich."

You know what that means. You've made a thousand sandwiches. The knowledge is so obvious it's invisible — which is exactly the problem. The robot can't see what's invisible to you.

Attempt #1 // 03
you@kitchen:~$ put the peanut butter on the bread

Reasonable. Clear, even. So the robot does it — literally. It picks up the jar. It places the jar. On the bread.

✓ INSTRUCTION FOLLOWED EXACTLY

It is not broken. It is not being difficult. It did what you said.

output: jar.placeOn(bread) // technically correct

Why It Failed // 04

The robot was right.
Your instruction was wrong.

WHAT YOU SAID

Put the peanut butter on the bread.

Two nouns, one position. Unambiguous to a machine.

WHAT YOU MEANT

Open the jar, take a knife, scoop a spreadable amount, and distribute it across one face of one slice.

~12 hidden steps, all assumed.

The gap between what you said and what you meant has a name. Two, actually — and you'll meet them every day as a programmer.

The Whole Point // 05

Giving
instructions
is hard.

Not because you're bad at it. Because language leans on shared understanding, and a machine shares none of yours.

Attempt #2 // 06

You learn. You get specific:

you@kitchen:~$ open the jar and spread the
  peanut butter

Better! But you never said with what. The robot has no knife in its instructions — so it improvises with the only tool it has. Itself.

✕ NEW FAILURE UNLOCKED

Fixing one ambiguity reveals the next. This is the job.

The Hidden Knowledge // 07

Every order you gave
quietly assumed things.

Humans fill gaps automatically. The robot exposes every gap you didn't know you left:

  • A jar must be opened before its contents exist to you
  • "Spread" needs a tool — a knife, held a particular way
  • "On the bread" means one face of one slice, not on top of the loaf
  • A sandwich implies two slices, and a second one to close it
  • "Some" peanut butter is a quantity the robot can't guess

These unstated assumptions are called preconditions. Naming them is half of programming.

The Fix, Part 1 // 08

Break it down
until nothing is assumed.

Decomposition: split one fuzzy command into atomic steps a literal machine can't misread.

That diamond is a decision. That loop is iteration. You're already writing control flow.

The Fix, Part 2 // 09

Order is part of the meaning.

Same steps, wrong sequence, different (and worse) sandwich. The robot won't reorder them for you.

CORRECT ORDER 
flowchart LR
    O[open jar] --> S[spread] --> C[close sandwich]
    style O fill:#0e1826,stroke:#6ee7a0,color:#6ee7a0
    style S fill:#0e1826,stroke:#6ee7a0,color:#6ee7a0
    style C fill:#0e1826,stroke:#6ee7a0,color:#6ee7a0
        
open jar -> spread -> close
SWAPPED 
flowchart LR
    C2[close sandwich] --> S2[spread] --> O2[open jar]
    style C2 fill:#0e1826,stroke:#ef6b53,color:#ef6b53
    style S2 fill:#0e1826,stroke:#ef6b53,color:#ef6b53
    style O2 fill:#0e1826,stroke:#ef6b53,color:#ef6b53
        
close -> spread -> open jar

Spreading butter on a closed sandwich. Opening a jar you no longer need.

A program is steps in an order. Change the order, change the result.

Attempt #3 // 10

A full, decomposed, ordered, assumption-free spec:

// sandwich.spec
get(bread, 2)
open(jar)
grip(knife)
while not covered(slice[0]):
  scoop(knife, jar)
  spread(knife, slice[0])
stack(slice[1], onto=slice[0])
serve()
✓ SANDWICH ACHIEVED
The Reveal // 11

You just wrote
a program.

The robot was never the point. The robot is every literal machine you'll ever instruct — and the failures you saw have real names you'll use all term:

Broke the grammar — bad word order, missing piece
→
syntax error
Grammar fine, the action is impossible — spread with no tool
→
semantic error
It ran, then fell over mid-task
→
runtime error
It worked perfectly — and made the wrong thing
→
logic error

Same robot. Same literal-mindedness. Whether it's a compiler, an interpreter, or the AI you'll prompt later — they all make sandwiches exactly the way you ask.
